# Research Context Synthesis

## Current scientific mainline

Across the local context, execution ZIP, and latest Notion section, the stable question is:

> Under a specified region, scale, information condition, cognitive task, and subject/agent, which visual or spatial elements can be converted from candidates into verified functional landmarks through controlled task-relevant intervention?

The stable mechanism is:

```text
scope specification
-> multi-source candidate generation
-> identity/location/spatial-relation representation
-> Original / Removal / Identity replacement / Location replacement / Matched control
-> verified / rejected / uncertain
-> relation to place, edge, route, and region
-> spatial cognition / cognitive-map proxy / navigation
```

## Teacher/user discussion constraints captured in Notion

- Navigation is a major behavioral validation route, not the only boundary; the target is spatial cognition.
- Spatial entropy may be a statistical candidate-generation signal, but it cannot define verified landmarks by itself.
- The ten routes are described as existing high-quality trajectories, but this remains an unverified asset claim until file inspection.
- Most importantly, data feasibility must be controlled by human review: failure to produce a result may reflect an unsuitable dataset rather than a method failure, and Paris should be replaced if it cannot support the intended experiment.

## Execution correction adopted in this audit

The immediate work is `Paris Data and Task Feasibility Audit`, not `Functional Landmark Pilot` or `Landmark Assistance Pilot`.

The feasibility audit must determine:

- what assets actually exist;
- whether they join at case level;
- what the topology and routes support;
- what the historical RL system actually consumes and learns;
- what humans see in route, intersection, and area review boards;
- which of Go / Adapt / Replace is supported.

No new literature should become an operation merely because it is recent. It enters the candidate knowledge base first and becomes operational only when it solves an observed audit, design, or validation problem.
